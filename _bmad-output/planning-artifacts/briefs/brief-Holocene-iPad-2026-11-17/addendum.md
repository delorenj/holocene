## Realistic approaches

These are engineering comparisons, not measured estimates. Framework suitability was checked against official documentation; no framework version is pinned by this brief.

| Approach | Reuse and voice reliability | Call |
| --- | --- | --- |
| Safari / Home Screen web app | Maximum existing React reuse and no signing requirement. Capture is supported in WebKit, but browser unlock, current full-file playback, fast-path exclusion, codec variation, and suspension remain gaps. Web capability alone does not prove daily voice parity. | Useful baseline during the spike; not the committed full-experience deliverable. |
| Thin Swift shell + WKWebView + native audio | Reuses the actual current UI/TypeScript and backend while replacing only Android-specific adapters. Gives AVFoundation control over capture, playback and interruptions. Requires a secure asynchronous bridge, compatible asset versioning, native-owned lifecycle/state, and proven identity transport. | Recommended first candidate after inspecting the brownfield app. Retain only if the device spike passes. |
| Fully SwiftUI + AVFoundation | Direct native lifecycle, accessibility and tablet layouts; retains backend but recreates the current web workflow and ledger/presentation logic. | Strong fallback if bridge/UX reliability fails. The Apple researcher preferred this before factoring in the existing shared React UI. |
| Kotlin Multiplatform / Compose | Official docs list iOS support as stable. Could share proven pure Kotlin policies, but this app’s interface is React, not Compose; a Kotlin UI migration is not free reuse. Native Apple audio integration and Xcode are still required. | Revisit if actual Android/iPad shared business logic warrants it, not just because Android uses Kotlin. |
| Tauri 2 / Rust | Can reuse React and later desktop packaging. Official mobile plugins still call Swift/Kotlin, so Rust does not remove the Apple audio adapter or Mac/signing lane. No local compute/codec bottleneck has been measured. | Defer. Consider for desktop packaging or a measured portable core; no server/client rewrite now. |

**Decision basis:** Momo **Pillar 2 — Dogfood the Platform** favors keeping the proven agent/voice stack; **Pillar 3 — Build LEGO, Not Statues** and its second-use rule support a narrow reusable client-capability seam now that a second native platform is requested; **Pillar 4 — Gang of Four by Default** names the platform **Adapter** boundary. Global `it-behaves-like-it-looks` favors real native-audio/device evidence over a nominal installable wrapper; `zero-dollar-defaults` favors existing Mac, identity and speech infrastructure before new subscriptions. This is a private-use plan; no payment or revenue hypothesis was invented to invoke Pillar 1. Proposed stack/default choices are not operator-approved architecture decisions.

## Apple constraints verified from primary sources

Consulted 2026-11-17. Apple’s documentation is live and may describe APIs newer than Jarad’s installed OS. Verify availability against the selected deployment target; a docs page is not an on-device test.

1. **Microphone access requires a purpose string and permission.** `NSMicrophoneUsageDescription` is required for microphone APIs. `AVAudioSession.playAndRecord` covers alternating or simultaneous input/output; the product chooses half-duplex, not continuous listening. [Purpose string](https://developer.apple.com/documentation/bundleresources/information-property-list/nsmicrophoneusagedescription) · [playAndRecord](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playandrecord).
2. **Background audio is a declared activity, not a permanent worker.** Apple documents `UIBackgroundModes=audio` for legitimate continued audio; ordinary background apps are typically suspended. A playing reply and a new reply arriving after silent waiting are different cases. No silent tracks, hidden mic recording, VoIP/PushKit misuse, or embedded keepalive clock to prevent suspension. The first release safely stops/saves capture on background transition rather than promising background recording. [Background execution modes](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes.md).
3. **Audio interruptions and route changes are normal.** Observe the APIs appropriate to the deployed OS; pause or recover truthfully. Headphone disconnect should pause rather than expose private speech on speakers. Some iPads hardware-mute the built-in mic when a Smart Folio closes. Latest docs also describe newer lifecycle notifications; do not require those on an older iPad. Existing phone on-call signals may still apply but do not replace local iPad audio-session handling. [Interruptions](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions) · [Route changes](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes).
4. **Silent push cannot guarantee a spoken answer.** APNs background notifications are low-priority, throttleable and not guaranteed; Apple advises sending no more than two or three background notifications per hour and allows 30 seconds of work when one is delivered. A held notification can be discarded after termination. Notification sound names refer to device-resident files or the system sound, not arbitrary generated reply URLs. Plan a privacy-safe “reply ready” alert and tap-to-open later; permission denial leaves foreground recovery functional. [Background updates](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app) · [Notification payload and sounds](https://developer.apple.com/documentation/usernotifications/generating-a-remote-notification).
5. **WebKit capture exists; lifecycle parity is unproved.** WebKit documents `MediaRecorder`, feature detection, MP4/AAC capture, and `getUserMedia` in an authorized WKWebView. Its historical introduction article does not define every current codec or guarantee lock/suspension behavior. Probe the target OS and actual backend files. [WebKit MediaRecorder](https://webkit.org/blog/11353/mediarecorder-api/).
6. **Use supported native authentication and storage.** `ASWebAuthenticationSession` supports a web-service login and app callback; Keychain stores small secrets. Neither automatically authenticates the separate webview. A compatible token/session exchange remains an implementation design and test requirement. [Web authentication](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession) · [Keychain](https://developer.apple.com/documentation/security/keychain-services).
7. **Installation is not an Android APK flow.** Free Personal Team provisioning expires after seven days and requires rebuilding/reinstalling. Developer Program membership supplies App Store Connect/TestFlight. Internal testers are eligible App Store Connect users, not just an arbitrary invitation email; the first external beta requires review. TestFlight builds last up to 90 days from upload and testers install through Apple’s TestFlight app/invitation. No enrollment or paid service was purchased or assumed. [Developer accounts](https://developer.apple.com/help/account/basics/about-your-developer-account/) · [TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview) · [Internal testers](https://developer.apple.com/help/app-store-connect/test-a-beta-version/add-internal-testers).
8. **A supported macOS/Xcode lane is required for native builds.** Verify the existing fleet executor and SDK compatibility, not a Linux cross-compile promise. KMP/Tauri do not remove Apple’s build prerequisites. This host is Linux with no `xcodebuild`; the presence or readiness of a remote Mac was not checked. [Apple Xcode requirements](https://developer.apple.com/support/xcode/) · [KMP platforms](https://kotlinlang.org/docs/multiplatform/supported-platforms.html) · [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) · [Tauri mobile plugins](https://v2.tauri.app/develop/plugins/develop-mobile/).
9. **A future public release needs its own review fit.** A web wrapper is not automatically App Store-acceptable; native value, privacy, account access for review and correct background-mode use need review against current rules. Private beta delivery is the first target, not a claim of App Store approval. [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality).

## Unknowns and ownership

- **Implementation preconditions:** PM/client executor discovers device/OS and the existing Mac/signing/release lane; no new hardware or subscription spend is the default. If credentials, passkeys, or physical pairing are unavailable, batch the exact owner-only step rather than asking for product sign-off.
- **Technical spike gates:** client/audio worker proves codec, bridge, lifecycle and tablet fit; backend worker proves iPad fast-path semantics, collision-free recording identity and reply ownership. Roles are proposed responsibilities, not worker assignments.
- **Before private beta:** identity owner/client developer verifies live edge and storage authorization, then implements the narrow compatible operator session flow. Device IDs never become authentication by assertion.
- **Product assumptions:** foreground-first use, no car-to-iPad handoff in the first release, and private single-operator distribution. Revisit if Jarad later makes locked-screen incoming speech or seamless cross-device context essential; do not fake those features with push or copied device IDs.
