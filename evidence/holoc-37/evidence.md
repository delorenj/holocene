## Android rules and FCM/WIU conclusion

[Android 17 background audio hardening](https://developer.android.com/about/versions/17/changes/bg-audio): all apps on Android 17 need a visible activity **or a foreground service not of type SHORT_SERVICE** for background playback, audio-focus and volume/ringer calls, irrespective of target SDK. Target-37 background apps additionally need a foreground service with **WIU capability**; the target-37 waiver applies **only** to streams `USAGE_ALARM` where exact alarm permission has actually been granted. Failed playback/volume can be silent; failed focus returns `AUDIOFOCUS_REQUEST_FAILED`; testing `throw` makes failures loud and **also enforces WIU for target 36 and even granted-alarm streams** (unlike ordinary target-37 waiver). `AudioHardening level: full` means FGS lacking WIU, `partial` means no FGS. Visible activity and user-initiated FGS start confer WIU; background-started FGS mostly do not. Its named exceptions with WIU are explicit user intent (notification/widget/media-key) or system delegation, **not FCM receipt**. A `mediaPlayback` FGS has no additional runtime prerequisites and is appropriate for continuing background media ([FGS type reference](https://developer.android.com/develop/background-work/services/fgs/service-types)); the type alone does not establish WIU.

[FGS background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start) explicitly allow *starting* an FGS upon a genuinely high-priority FCM delivery, but note high priority can be downgraded, in which case starting an FGS can throw `ForegroundServiceStartNotAllowedException`. **These are two distinct permissions/gates:** FCM exemption for background *start* does not confer Android-17 *audio WIU*. On documentation alone, a service newly started by FCM while the app remains backgrounded has **no documented WIU grant**, so the proposed Cloud high-priority-FCM → on-demand mediaPlayback FGS cannot be assumed to autoplay normal `USAGE_MEDIA` at target 37; expect suppressed playback/focus/volume unless it had WIU through another eligible, user-visible initiation or some independently demonstrated exception. There is no FCM receiver in today's manifest, and **no FCM delivery, target-37 build, or WIU-negative emulator probe was executed**. Thus the above is a **documentation-backed negative design conclusion, not a measured FCM failure**; platform-specific exceptions should be measured with a controlled emulator-only FCM receipt before a final product decision. For alarm streams, a granted exact-alarm permission is an *ordinary target-37* audio waiver, not a general waiver for media, nor an FCM WIU grant, nor proof that the `throw` test mode permits an FCM start.
